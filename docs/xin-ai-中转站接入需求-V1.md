# xin.ai 模型中转站接入需求（内部文档 · 不可对外）

> 版本 v1.0 ｜ 2026-10-29 ｜ 状态：待评审
> **本文档含采购成本与渠道策略，禁止随开发交付物一并提供给外部客户。**

---

## 0. 背景与定位

xin.ai 是自营 AI 内容生产平台（对标 DAAI / susu.da-ai.cc），商业模式为「积分充值 → 按生成消耗积分」。

平台自身不直接持有各厂商官方账号，而是通过**模型中转站（聚合服务商）**统一拿货。这一决策带来三��收益与一项风险：

| 项 | 内容 |
|---|---|
| 收益 1 · 成本 | 中转站拿货价通常低于官方刊例价 10~30%，直接转化为毛利 |
| 收益 2 · 账期 | 中转站多为预充值，单次充值门槛低，适合冷启动 |
| 收益 3 · 一站接入 | 一个 OpenAI 兼容端点覆盖多厂商模型，免去逐家开通与资质审核 |
| **风险** | **中转站稳定性、模型版本一致性、合规性均不可控** |

因此本需求的全部设计围绕一个核心目标：

> **让用户完全感知不到中转站的存在，同时保证中转站挂掉时平台不掉线。**

| 项 | 指标 |
|---|---|
| 切换延迟 | 通道失效到自动切换完成 ≤ 3 秒（不重试原通道） |
| 降级不丢单 | 切换过程任务不失败、不重复扣费；最终成功或全额退款 |
| 配置生效 | 后台修改售价/通道配置 ≤ 30 秒生效，无需重启 |

| 密钥安全 | 中转站 API Key 不出现在前端、不落日志明文、可热轮换 |

## 2. 接入架构

### 2.1 分层结构

```
┌──────────────────────────────────────────────────────────┐
│  业务层 Service：报价 → 冻结 → 提交 → 轮询 → 结算         │
├──────────────────────────────────────────────────────────┤
│  渠道路由层 Channel Router  ★新增                       │
│    · 按能力域选择通道（中转优先 / 官方兜底）              │
│    · 熔断器状态机（CLOSED / OPEN / HALF_OPEN）           │
│    · 限流器（分通道独立配额）                            │
│    · 成本采集钩子（记录真实拿货成本）                    │
├──────────────────────────────────────────────────────────┤
│  Adapter 层：OpenAI-Compatible Adapter / 各厂商专用 Adapter │
│    · 请求转换、轮询/回调解析、错误归一化                 │
│    · ★ base_url 与 api_key 由渠道配置注入，不硬编码       │
├──────────────────────────────────────────────────────────┤
│  官方直连通道（fallback）   │   中转站通道（primary）      │
└──────────────────────────────────────────────────────────┘
```

### 2.2 渠道配置数据结构

新增数据表 `model_channels`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `name` | varchar | 渠道名，如 `relay-a` / `official-volc` |
| `provider` | varchar | `relay`（中转）/ `official`（官方） |
| `capabilities` | jsonb | 覆盖的能力域列表，如 `["video","image"]` |
| `base_url` | varchar | 接入点，**入库可查、后台可改**（中转站地址本身不是机密） |
| `secret_ref` | varchar | 密钥引用（指向密钥管理服务，非明文；密钥本身不入库） |
| `priority` | int | 优先级，数字越小越优先 |
| `status` | varchar | `active` / `paused` / `degraded` |
| `rpm_limit` | int | 该通道独立 RPM 上限 |
| `qps_limit` | int | 该通道独立 QPS 上限 |
| `cost_ratio` | decimal | 拿货成本系数，1.0 = 刊例价，0.85 = 中转 85 折 |
| `health_check` | jsonb | 健康检查配置（间隔、超时、判定标准） |
| `circuit_state` | varchar | `closed` / `open` / `half_open` |
| `created_at / updated_at` | timestamptz | |

**关键设计**：**接入点（base_url、模型名、超时、重试、优先级）全部存数据库，后台可改**；只有**密钥本身**通过密钥管理服务保存，数据库里只存引用。配置加载走缓存 + 主动失效，保存后 ≤ 30 秒生效，无需重启。

好处：
- 换中转站、给某个模型单独换接入点，都是后台点几下，不改代码、不重新部署
- 密钥仍不落库，数据库泄露不会导致密钥外泄
- 每个模型可以独立配置，文生图走 A 站、文生视频走 B 站都可以

### 2.3 ★ 模型接入点配置表（后台可配的核心）

`model_channels` 定义「一条通道」，但平台需要的是「**每个模型分别配接入点**」——比如文生图走 A 站、文生视频走 B 站、数字人口播走官方直连。因此再有一张 `model_endpoints` 表，把模型键映射到具体接入点。

**表结构 `model_endpoints`**：

| 字段 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `id` | uuid | | 主键 |
| `model_key` | varchar | `image.text2image.2k` | 模型键，与能力域路由表的 key 对应 |
| `capability` | varchar | `image` | 能力域 |
| `display_name` | varchar | LC Image 2.5 Pro | 前台展示名 |
| `channel_id` | uuid | → `model_channels.id` | 走哪条通道 |
| `base_url` | varchar | `https://api.relay-a.com/v1` | **接入点，入库可改，后台可编辑** |
| `upstream_model` | varchar | `lc-image-2.5-pro` | 上游真实模型名（中转站与官方可能不同） |
| `secret_ref` | varchar | `sm://relay-a/image` | 密钥引用，密钥本体在密钥管理服务 |
| `timeout_ms` | int | 30000 | 单次调用超时 |
| `max_retries` | int | 2 | 通道内重试次数（不跨通道） |
| `rpm_limit` | int | 600 | 该接入点的 RPM 上限 |
| `enabled` | bool | true | 是否启用 |
| `is_default` | bool | false | 是否为该能力域的默认接入点 |
| `cost_ratio` | decimal | 0.85 | 拿货成本系数 |
| `sort_order` | int | 10 | 同能力域多接入点的排序（= 降级顺序） |
| `config_json` | jsonb | `{"resolution":"2K","n":1}` | 能力域特有的参数映射 |
| `updated_by / updated_at` | | | 改接接入点留痕 |

**为什么要有这张表（三个具体收益）**：

1. **每个模型可单独换接入点** —— 中转站只支持部分模型时，不支持的模型单独挂官方直连，互不影响
2. **换站不用改代码** —— 中转站 A 挂了，把 `channel_id` 指到 B，或直接改 `base_url` 即可
3. **上游模型名可以不同** —— 中转站叫 `seedance-2.0`，官方叫 `doubao-seedance-2-0`，映射关系存在 `upstream_model`，前台仍显示统一名称

**表间关系**：

```
model_channels（通道：一家中转站 / 一家官方）
    │  1
    │
    │  N
model_endpoints（接入点：文生图 → A站 / 文生视频 → A站 / 数字人 → 官方）
    │  N
    │
    │  1
ability_pricing（售价积分：文生图 2K = 5 积分）
```

**后台配置界面（新增页签「模型接入」）**：

| 区域 | 内容 |
|---|---|
| 通道列表 | 通道名、类型（中转/官方）、状态、覆盖能力域、优先级、余额（若可查） |
| 接入点列表 | 按能力域分组，每行显示：模型键、展示名、当前通道、base_url、上游模型名、超时、启用开关、排序 |
| 行内操作 | 启用/停用、复制、测试连通性（发一次最小成本探针）、查看最近 24h 成功率 |
| 批量操作 | 按能力域批量切通道、按通道批量改 base_url |
| 变更留痕 | 谁在什么时候把哪个模型从 A 切到 B，记录可回溯 |

**配置加载与生效机制**：

```
启动：SELECT * FROM model_endpoints WHERE enabled = true → 载入内存缓存（Map<model_key, Endpoint>）
后台保存：UPDATE model_endpoints → 主动失效该 model_key 的缓存项 → ≤ 30 秒内新任务用新配置
运行时：ChannelRouter 按 model_key 取 Endpoint → 取 channel_id 的通道做熔断判定 → 调 Adapter
```

**测试连通性**（后台按钮）：用最小成本探针（如 1K 图 1 张）真实调用一次，返回耗时、是否成功、错误信息、上游返回的模型标识。**同时用于版本一致性巡检**（§5.3）。

### 2.4 成本系数 `cost_ratio` 的作用

这是本需求的**商业核心**。同一能力，走中转和走官方的真实成本不同：

```
真实成本 = 官方刊例成本 × cost_ratio
```

- 中转通道：`cost_ratio = 0.85`（按实际谈定）
- 官方通道：`cost_ratio = 1.00`

毛利核算用**实际发生的通道**的 `cost_ratio`，这样「用户选了哪条通道」和「你赚了多少」能对上账。

## 3. R1/R2：配置化与双通道

### 3.1 R1 端点配置化

**现状问题**（已核实）：原站模型路由表 `api/v1/model-routes/public` 的字段为
`key / display_name / description / enabled / discount_rate / resolution_discounts`，
**不含 base_url** —— 说明接入点是硬编码在服务端代码里的，无法运营侧切换。

**改造要求**：

- Adapter 层统一从 `ModelEndpointRegistry` 获取接入点快照（`baseUrl` / `apiKey` / `upstreamModel` / `timeoutMs` / `configJson`）；Java 侧由 `ModelRequest` 携带，Adapter 实现类不得持有硬编码的上游地址
- 所有 endpoint / apiKey 读取统一走 `ModelEndpointRegistry`，禁止在代码中硬编码任何 URL
- 启动时从 `model_endpoints` + `model_channels` 加载全量配置进内存缓存
- 后台保存配置后主动失效缓存（Redis `RTopic` 广播到所有实例），≤ 30 秒生效，**无需重启进程**

**验收**：仅通过后台界面修改，即可在不重新构建镜像、不重启服务的情况下切换任意模型的接入通道。

### 3.2 R2 通道选择策略

**默认策略（推荐）**：

```
优先级排序 → 中转站（primary）
                ↓ 失败/超时/限流
            官方直连（fallback）
```

**何时该用官方直连**（不走中转）：

| 场景 | 原因 |
|---|---|
| 图片生成（LC Image / 百炼） | 石材客户上传厂房/展厅实拍属商业机密，部分中转站会记录 prompt 与素材 |
| 音色克隆 / 数字人口播 | 涉及声音与肖像授权材料，敏感度最高 |
| 高价值长视频任务 | 单条成本高，中转站波动造成的损失大 |
| 对账存疑时 | 抽检比对中转与官方的效果差异 |

**策略可配置**：在 `model_channels.capabilities` 上按能力域分别指定「中转优先」或「官方优先」。

## 4. R3/R4：健康检查、降级与熔断

### 4.1 健康检查

| 项 | 配置 |
|---|---|
| 检查方式 | HTTP `GET {base_url}/models`（OpenAI 兼容）或轻量推理探针 |
| 间隔 | 60 秒（可在后台调整） |
| 超时 | 10 秒 |
| 判定失败 | 连续 3 次失败 → 判定不可用 |
| 判定恢复 | 连续 2 次成功 → 判定可用 |

### 4.2 熔断器状态机

```
        失败率 > 50%（窗口 20 次请求，最少 10 次）
CLOSED ──────────────────────────────→ OPEN
   ↑                                      │
   │ 连续 2 次成功                        │ 冷却 60 秒
   │                                      ↓
   └──────────────────── HALF_OPEN ←─────┘
                          │
                   放行 1 次探针
                   成功 → CLOSED
                   失败 → OPEN（冷却翻倍，上限 10 分钟）
```

**Java 实现**：直接用 Resilience4j `CircuitBreaker` 配置上述参数（`failureRateThreshold=50`、`slidingWindowSize=20`、`minimumNumberOfCalls=10`、`waitDurationInOpenState=60s`、`permittedNumberOfCallsInHalfOpenState=1`），不手写状态机。通道维度：每个 `model_channels.id` 一个 CircuitBreaker 实例。

### 4.3 自动降级流程（R3 核心）

```
用户提交任务
    ↓
渠道路由层按 priority 选通道（中转）
    ↓
提交 → 超时(30s) / 429 限流 / 5xx / 连接失败
    ↓
记录失败原因，标记该次失败
    ↓
自动切换到下一优先级通道（官方直连）
    ↓
用相同参数重新提交（幂等键保证不重复扣费）
    ↓
成功 → 正常结算，usage_record.channel = 实际成功通道
失败 → 所有通道都失败 → 全额退回冻结积分
```

**必须保证的三条**：

1. **不重复扣费**：整个切换过程只冻结一次积分，最终按一次结算
2. **不丢任务**：切换对用户透明，用户侧不感知
3. **不重复执行**：幂等键（`idempotency_key`）贯穿全部通道尝试

### 4.4 中转站特有故障的处理

| 故障 | 表现 | 处理 |
|---|---|---|
| 假成功 | 中转返回成功但结果为空/损坏 | 结果校验（文件大小/格式/时长），异常按失败处理并切换 |
| 模型版本不符 | 返回的模型不是期望版本 | §5.3 版本巡检拦截；单次任务内按"降级生成"处理 |
| 超时但实际已生成 | 中转超时，上游仍在跑 | 用**同一幂等键**查询，不重新提交；查不到再切通道 |
| 计费异常 | 中转站扣费与实际调用不符 | 日终对账（§5.2）差异告警 |

## 5. R6/R7/R9：成本、账务与一致性

### 5.1 R6 成本采集与毛利核算

`usage_record` 表新增字段：

| 字段 | 说明 |
|---|---|
| `channel_id` | 实际使用的通道 |
| `provider` | `relay` / `official` |
| `upstream_cost` | 真实拿货成本（元），= 刊例成本 × 该通道 `cost_ratio` |
| `official_cost` | 同能力按官方刊例计算的成本（用于对比） |
| `saved_cost` | `official_cost − upstream_cost`，即中转站带来的节省 |
| `points_charged` | 向用户扣的积分 |
| `revenue` | 积分 × 1 元锚定 |
| `gross_margin` | `(revenue − upstream_cost) / revenue` |

**毛利日报**（R6 核心产出）：

| 维度 | 拆分 |
|---|---|
| 按能力域 | 每个能力的收入 / 成本 / 毛利率 |
| 按通道 | 中转站 vs 官方直连的毛利率对比 |
| 按模型 | 具体到 Seedance 2.5 / Wan 3.0 等 |
| 中转站节省累计 | `sum(saved_cost)`，即中转站为你创造的额外利润 |

**熔断线**：连续 3 日某能力域毛利率低于目标值 15 个百分点 → 自动下调该能力售价积分或暂停折扣。

### 5.2 R7 渠道账务对账

| 频率 | 内容 |
|---|---|
| 日终 | 与中转站账单核对：调用次数、Token/秒数、金额 |
| 差异阈值 | 差异率 > 0.5% 触发告警；> 2% 自动暂停该通道 |
| 周期 | 月结对账（中转站账单通常月结，需注意账期与充值节奏） |
| 异常处置 | 差异逐笔核查；确认中转站多扣则申诉，漏扣则补记成本 |

**注意**：预充值模式下的**余额预警**——中转站余额低于阈值时告警，否则某天余额耗尽会导致全站视频生成不可用。

### 5.3 R9 模型版本一致性巡检

中转站的最大隐患是**同名模型返回不同版本**（如中转的 "seedance-2.0" 实际是更早的版本）。

**巡检机制**：

| 频率 | 动作 |
|---|---|
| 每日 | 对每个走中转的能力域，跑 1 次最小成本探针任务，记录输出指纹 |
| 每周 | 抽样 10 条中转产出与官方直连产出做主观对比（人工评审） |
| 每月 | 拉取中转站返回的模型清单，与配置期望清单比对 |
| 异常时 | 立即切该能力域到官方直连，并通知运营 |

**指纹记录**：模型版本标识 + 输出特征（分辨率/时长/风格一致性），存入 `model_channel_health` 表。

## 6. R5 售价积分可配置 + R10 透明度策略

### 6.1 R5 售价积分后台可配

**需求**：平台运营方需能随时调整每个能力的售价积分，以应对成本波动、竞品定价、促销策略。

**设计**：售价从硬编码改为**配置表驱动**。

新增表 `ability_pricing`：

| 字段 | 说明 |
|---|---|
| `capability` | 能力域，如 `video.standard` |
| `model_key` | 模型键 |
| `spec` | 规格，如 `720P` / `5秒` / `2K` |
| `points` | 售价积分（可调） |
| `cost_override` | 成本覆盖（可选，用于特殊定价） |
| `discount_rate` | 折扣率（复用原路由表字段） |
| `effective_from` | 生效时间 |
| `version` | 版本号，改价留痕 |
| `updated_by` | 操作人 |

**改价生效**：后台修改 → 缓存失效 → ≤ 30 秒生效，无需重启。

**与成本的关系**：
```
售价积分 = ceil(官方刊例成本 × cost_ratio_实际通道 ÷ (1 − 目标毛利率))
```
后台改价时，系统实时显示「按当前成本，这个售价的毛利率是 X%」，并给出警告：
- 毛利率 < 30% → 黄色警告
- 毛利率 < 10% 或 售价 < 成本 → 红色警告，禁止保存

**改价审计**：所有改价记录操作人、时间、前后值、理由，可回溯、可导出。

### 6.2 定价表的「成本」列怎么办

内部文档里的定价表应显示**双成本**：

| 能力 | 售价积分 | 官方成本 | 中转成本(85折) | 中转毛利率 | 官方毛利率 |
|---|---|---|---|---|---|
| 文生视频 720P 5秒 | 14 | ¥5.85 | ¥4.97 | 64.5% | 58.2% |
| 全模态视频 1080P 5秒 | 50 | ¥22.23 | ¥18.90 | 62.2% | 55.5% |
| 图片口播 60秒 | 160 | ¥70.37 | ¥59.81 | 62.6% | 56.0% |

### 6.3 R10 用户侧降级透明度

**原则**：让用户感知「稳定」，不感知「渠道」。

| 场景 | 用户看到 |
|---|---|
| 中转正常 | 无任何提示 |
| 中转失败切官方，**官方成功** | 无提示（成功就是成功） |
| 中转失败切官方，**官方也失败** | 「当前服务繁忙，请稍后重试」+ 积分已全额退回 |
| 中转站全局不可用 | 「服务维护中，已自动切换至备用通道」+ 提示积分已退 |

**绝对不告诉用户**："中转站""我们的上游""第三方代理"。对外统一表述为「备用通道」。

## 7. R8 限流与配额

| 项 | 说明 |
|---|---|
| 分通道限流 | 每个通道独立 RPM/QPS 令牌桶，不共用配额（Redisson `RRateLimiter`，按 `channel_id` 分实例） |
| 用户级限流 | 防刷：同 IP/同账号的生成频率上限，超限排队而非直接失败 |
| 能力级队列 | 沿用 A4 的能力域分队列（Redisson `RDelayedQueue`，每个能力域一个队列实例） |
| 中转站配额感知 | 从中转站 API 拉取余额/配额（若其支持），余额不足时告警并提前降级 |

**余额告警阈值**（建议）：
| 级别 | 余额 | 动作 |
|---|---|---|
| 提示 | < 30 天用量 | 站内通知运营 |
| 警告 | < 14 天用量 | 邮件 + 即时通知 |
| 紧急 | < 7 天用量 | 自动暂停低优先级能力域，优先保核心业务 |

## 8. 安全与合规

### 8.1 密钥安全

| 要求 | 做法 |
|---|---|
| 不入代码库 | endpoint / 模型名 / 超时 / 优先级全部入库，代码里不出现任何具体 URL |
| 密钥不入库明文 | `model_channels.secret_ref` 只存引用，密钥本体在密钥管理服务 |
| 不入日志 | 日志脱敏规则覆盖 `api_key`、`authorization` |
| 可轮换 | 支持双 Key 灰度切换（old/new 并存，验证通过后下线 old） |
| 前端不可见 | 任何接口不返回渠道密钥 |

### 8.2 用户数据与素材

| 要求 | 说明 |
|---|---|
| 敏感数据优先官方直连 | 石材厂房/展厅实拍、数字人形象照与录音授权文件 → 官方通道 |
| 中转站的数据处理 | 采购前确认其数据留存策略与日志脱敏能力；无法确认则该能力域不走中转 |
| 用户协议 | 明确告知用户「生成内容将提交至第三方模型服务处理」 |

### 8.3 合规红线

| 项 | 要求 |
|---|---|
| 内容安全 | 中转站若跳过或弱化内容审核，**不得用于对 C 端开放的能力域**；平台侧仍须自行审核 |
| 发票 | 中转站开票资质须正规，确保平台收入可正常开票给企业客户 |
| 实名 | 涉及付费内容生成的平台，须完成实名认证与内容审核资质 |
| 备案 | ICP 备案主体须为平台运营方本人或公司 |

## 10. 验收标准

| # | 验收项 | 判定标准 |
|---|---|---|
| 1 | 通道可切换 | 后台改配置后，全站模型通道完成切换，无代码改动、无重新构建、无需重启 |
| 2 | 降级不丢单 | 中转站全挂时，平台生成成功率下降 ≤ 3%，无任务丢失 |
| 3 | 不重复扣费 | 切换场景下 1000 次任务，扣费与实际调用一一对应，误差 0 |
| 4 | 自动恢复 | 中转站恢复后 5 分钟内自动重新纳入流量，无需人工干预 |
| 5 | 售价可配 | 后台改价后 30 秒内生效；售价 < 成本的改价被拒绝 |
| 6 | 成本可追溯 | 抽查 100 条任务，100% 可追溯到通道、真实成本、扣费积分 |
| 7 | 毛利报表 | 日报能拆到能力/通道/模型三级，毛利率与手工核算一致 |
| 8 | 密钥安全 | 全量日志扫描无密钥明文；数据库无密钥明文；接口响应无密钥 |
| 9 | 用户无感 | 中转正常时用户侧无任何渠道相关提示 |
| 10 | 对账 | 日终对账差异率 < 0.5% |
